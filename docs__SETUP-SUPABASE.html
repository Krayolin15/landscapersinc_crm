Going live with Supabase

About an hour, done once by the owner or an administrator. When you finish, every staff member signs in with their own email, sees only what their role allows, and the agent runs at 05:00 and 05:30 even when nobody has the app open.

You need:

  • a Supabase account; the free plan is enough to start, and Pro adds daily backups;
  • the unzipped landscapers-hq folder (it has the company records in data/seed/ and the documents in data/vault/);
  • the app open as the owner: Admin → Go live gives you the SQL for every step below, ready to copy or download;
  • Node.js 18 or newer and the Supabase CLI 1.215.0 or newer, for steps 6 and 9;
  • psql (it comes with PostgreSQL) for loading the company data in step 4. The SQL editor in the dashboard works for every other step.

Keep the service_role key and the database password to yourself. They never go into the app, a chat message or an email.

1. Create the project

  1. Supabase dashboard → New project. Choose region Africa (Cape Town) if offered; otherwise the nearest region. Save the database password in a password manager.
  2. Project Settings → API: copy the Project URL and the anon public key. You need them in step 8.
  3. Project Settings → Database → Connection string (URI): copy it for psql.

2. Authentication settings

Authentication → Providers → Email:

  • Turn Allow new users to sign up off. Staff accounts are created by an administrator only. Even if someone signs up, they get no access: every table requires a staff profile.
  • Keep Confirm email on.

Authentication → URL Configuration: set Site URL to the address where the app will live (see DEPLOY.html), for example https://hq.landscapersinc.co.za. Add the same address under Redirect URLs. Password-reset and sign-in links go there.

3. Create the database

In the app, open Admin → Go live and run steps 01 to 05 in this order. For each one: Copy SQL, then in Supabase SQL Editor → New query, paste and click Run. Each step is safe to run again.

StepWhat it does
01 TablesEvery table (76 record types), indexes, and the role helper functions
02 Security rulesRow Level Security on every table: the rules for who can read and change what (see SECURITY.html)
03 Who and whenWho and when on every record (cannot be faked), the audit log, profile protection, form-response categories
04 File storageThe private drive and avatars storage buckets and their access rules
05 Live updatesLive updates on every phone and PC

To use psql instead, click Download on each step and run the files from the folder you saved them in:

psql "<your connection string>" -f 01_schema.sql
psql "<your connection string>" -f 02_rls.sql
psql "<your connection string>" -f 03_triggers.sql
psql "<your connection string>" -f 04_storage.sql
psql "<your connection string>" -f 05_realtime.sql

4. Load the company data (private)

In Admin → Go live, step 06 Company data, click Download 06_seed.sql. It is built from the company records exactly as they came in the zip (not from changes made on this computer). Then, from the folder where you saved it:

psql "<your connection string>" -f 06_seed.sql

This loads all 2,364 records (clients, sites, contracts, invoices, quotes, staff, payroll, medicals, assets, fleet, forms and more). It runs in one transaction, so it loads completely or not at all. Re-running only refreshes records nobody has edited since.

The file is about 4 MB, which is too large for the dashboard SQL editor, so use psql. It holds private company data: delete it once it has loaded.

5. Staff logins

The data pack contains the four people who had logins in the old CRM: Jared, Anthony, Renesh and Wayne. Each needs a Supabase login, which is then linked to their existing profile so their history stays attached to them.

  1. Authentication → Users → Add user → Create new user for each person. Enter their email and a temporary password, and tick Auto Confirm User.
  2. In Admin → Go live, step 08 Link staff logins, type each person's email (leave it empty for anyone who does not need a login yet).
  3. Copy SQL, paste it into the SQL editor and Run. Each line reports what it did. It is safe to run again.
  4. Sign in to the app as the owner with the temporary password. You are asked to choose your own.

After that, add everyone else from Admin → Users in the app. It sends the invitation email through the admin-users function, so step 6 must be done first.

6. Edge Functions (server code)

The functions are plain JavaScript (supabase/functions/<name>/index.js). In the landscapers-hq folder on your computer:

supabase login
node tools__deploy-functions.js --project-ref <your project ref>

The project ref is the 20 letters in your project address (https://<ref>.supabase.co). The tool deploys all five functions. Because they are JavaScript rather than TypeScript, the Supabase CLI needs a supabase/config.toml that names each entry file; the tool writes it for you each time (it is not kept in the project). Useful options: --only <name> deploys one function again, and --dry-run shows what would happen without changing anything.

FunctionWhat it doesLogin check
admin-usersInvite, create, reset, suspend and delete staff logins (the only place the service key is used for people)Caller must be signed in as owner or admin
send-emailSends a message or invoice from Mail through ResendCaller must be signed in
ai-assistantOptional cloud mode for Sage AI (Claude)Caller must be signed in
agent-runThe 24/7 agent: 05:00 dispatch, 05:30 briefing, debtor reminders, expiry watchSecret header from the scheduler (no login check, because the scheduler has no login)
inbound-emailReceives company email from your provider and files it into Mail with triageSecret header from the provider (no login check)

The _shared folder is included automatically. If a deploy fails, the tool lists the usual fixes: run supabase login again, check the project ref, or, if Docker is involved, close Docker Desktop and run the tool again.

Secrets

Set them once. Anything left out simply switches that feature off.

supabase secrets set RESEND_API_KEY=<key from resend.com> MAIL_FROM="Landscapers Inc <accounts@your-domain.co.za>"
supabase secrets set CRON_SECRET=<long random string> INBOUND_SECRET=<another long random string>
supabase secrets set ANTHROPIC_API_KEY=<key from console.anthropic.com>
SecretUsed byNotes
RESEND_API_KEYsend-email, agent-runEmail sending. Verify your domain in Resend first
MAIL_FROMsend-email, agent-runSender address on a domain verified in Resend
CRON_SECRETagent-runThe same value goes into Vault in step 7
INBOUND_SECRETinbound-emailYour email provider sends it as the x-inbound-secret header
ANTHROPIC_API_KEYai-assistantOptional: without it Sage still answers everything from your data, just less conversationally
ANTHROPIC_MODELai-assistantOptional. Default claude-opus-5-5
ANTHROPIC_EFFORTai-assistantOptional: low, medium (default) or high
TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_WHATSAPP_FROMagent-runOptional WhatsApp reminders. Without them, WhatsApp messages wait in the approvals queue and are sent by hand with one tap

SUPABASE_URL, SUPABASE_ANON_KEY and SUPABASE_SERVICE_ROLE_KEY are provided to functions automatically. Never set them yourself.

To generate a random string:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"

Incoming email (optional)

Point your provider's inbound webhook (Resend inbound, Postmark, Mailgun or a Cloudflare Email Worker) at:

https://<project ref>.supabase.co/functions/v1/inbound-email

Add the header x-inbound-secret: <INBOUND_SECRET>. Emergencies notify every manager straight away; quotes, reschedules and proofs of payment are sorted automatically.

7. The 24/7 schedule

  1. Database → Extensions: enable pg_cron and pg_net.

  2. SQL Editor, with the same value as CRON_SECRET:

    select vault.create_secret('<the CRON_SECRET value>', 'agent_cron_secret');
  3. In Admin → Go live, step 07 The 24/7 schedule, type your project ref. Copy SQL, paste it into the SQL editor and Run.
JobSASTWhat it does
agent-morning-dispatch05:00 dailyPlans today's crew routes and postpones weather-affected visits
agent-executive-briefing05:30 dailyWrites the owner's briefing: overnight decisions, dispatch, approvals, money, alerts
agent-payment-remindersHourly, 07:00–18:00Debtor reminders at 3, 7 and 14 days overdue, and proof-of-payment matching
agent-expiry-watchHourly, 07:15–18:15Licences, certificates, medicals and documents nearing expiry

Check it is working in the app under Autonomous Core (every run and decision is listed there), or in the Cron page of the Supabase dashboard. From the SQL editor:

select jobname, status, start_time, return_message from cron.job_run_details order by start_time desc limit 20;

8. Point the app at Supabase

In js__settings.js (the only file you edit), with your values:

mode: 'supabase',
SUPABASE_URL: 'https://<project ref>.supabase.co',
SUPABASE_ANON_KEY: '<the anon public key>'

The anon key is meant to be public; Row Level Security protects the data. Never put the service_role key here. The app reads this file straight away, whether index.html is double-clicked or the app is hosted; nothing needs rebuilding.

Then publish the app (DEPLOY.html) without the data/seed/, data/vault/ and data-tools/ folders.

9. Upload the documents

The data pack already lists all 253 original documents and the place in Storage where each one belongs, and the documents themselves are already in the data/vault folder of the zip. Upload them once, from your own computer:

  1. Supabase → Project Settings → API: copy the Project URL and the service_role key.

  2. In the landscapers-hq folder (PowerShell), with your own values:

    $env:SUPABASE_URL="https://<project>.supabase.co"; $env:SUPABASE_SERVICE_ROLE_KEY="<service_role key>"; node tools__upload-vault.js

    It checks every file against its record (SHA-256) and uploads it to the private drive bucket. It is safe to run again: files already there are skipped. Close the PowerShell window afterwards so the key is gone.

The service_role key bypasses every security rule: use it only on your computer, only in that command, never in js__settings.js, a file in this folder or a browser.

Afterwards each document opens from its record and from Drive for the people allowed to see it. Confidential documents and the FINANCE and HR drives stay restricted (see SECURITY.html). The in-app importer (Drive → Import document vault, manager or above) still accepts a vault zip if you prefer to upload through the browser; node tools__build-vault.js … --zip <file> makes one.

10. Check it

  • Sign in as the owner: the Daily Briefing, clients, invoices and calendar show the company's records.
  • Sign in as a field worker: no payroll, medicals, bank accounts, FINANCE or HR drive, and no HR or incident form responses except their own.
  • Admin → System shows the mode, versions, service worker, storage and notification status.

Developers can prove every rule before going live with npm run test:sql: it runs all of the SQL against real Postgres and checks access for eight roles. npm run sql writes the same SQL to files in build/sql/ (step 06 holds private data, so build/ is never committed).

Updating later

  • New app version: publish the new files. Phones pick them up on their next load.
  • The database changed (the release notes say so): run steps 01–05 again from Admin → Go live. They are safe to re-run and never delete data.
