The company data pack

The folder data/seed/ holds every record taken from the company files, ready for the app: one JavaScript file per record type (browsers load these even when index.html is double-clicked) plus manifest.js, which lists them with their counts and the pack version. For Supabase the same records become step 06 of the go-live SQL (Admin → Go live), built from these files when you ask for it. This page describes what is in the pack without repeating any of the private content.

Where it came from

The company data zip was read file by file: the CRM and sales workbooks, invoices (April to July), income statements, KPI trackers, schedules and operations registers, staff and HR files, medicals, training records, fleet, assets and purchases, health and safety forms and policies, SOPs, strategy documents, marketing material, and the old CRM's own data. Nested zips were opened too. The facts were extracted into 37 structured knowledge files. tools__build-seed.js then maps them into the app's record types, with one mapper per area in the private data-tools/seed/.

Every record carries _src, the source file (and sheet, row or page) it came from, so any value can be traced back to the original document.

How it was checked

  • Validation: every record is checked against the same rules the app uses (required fields, dates, SA ID and phone formats, money, enumerations). Result: 0 errors. There are 87 warnings, all of them things to follow up rather than errors: 79 open leads have no follow-up date, 3 issued quotes have no issue date, and 5 phone numbers or emails are not in a valid format.
  • References: every link between records (a visit to its site, an invoice to its client, a file to its folder) was resolved. Result: 0 broken links.
  • Loading: npm run test:sql loads the step 06 SQL into real Postgres and confirms the count for every record type matches the pack exactly, and npm run test:browser loads the pack into a real browser and counts every record there too.
  • Money: amounts are stored in rand and calculated in exact cents. Each invoice line is checked (quantity × price = amount). Where the printed total differs from the printed lines, the printed total is kept and the difference is noted on the invoice, so the records match what the client received.

Data issues: what the source files disagree on

Where the company's own files contradict each other, have gaps or contain obvious slips (for example two different branch codes on two bank letters, a total that does not match its lines, or a name spelt two ways), the import keeps what the source says and records a data issue with the evidence and where to look. Nothing was guessed or quietly corrected.

What was deliberately left out

  • Clinical medical details: only fitness outcomes and expiry dates are stored. The clinical text stays in the original documents, which are confidential in the HR drive.
  • Old CRM password hashes: they are not in the step 06 SQL. Supabase logins are created fresh (see SETUP-SUPABASE.html). Local mode keeps salted hashes so the four staff can sign in and must then change their password.

Rebuilding the pack

With the extracted knowledge files and the private data-tools/ folder (its mappers contain staff names and contact details, so they are never in git):

node tools__build-seed.js --knowledge <folder with the knowledge json files>

The output goes to data/seed/ (the record files, manifest.js and validation-report.js). Add --strict to stop on any error. --base data/seed --only <mapper numbers> adds documents sent later on top of the existing pack without re-reading every original file.

A rebuilt pack loaded into local mode only refreshes records nobody has edited since the last import; anything a person changed is kept. In Supabase, re-running step 06 behaves the same way.

The document vault

data/vault/ holds the 253 original files, laid out as <shared drive>/<folder>/<file>, exactly each file record's vault_path. The app opens each document straight from there. node tools__build-vault.js <company-data.zip> <vault-index.json> --extra landscapers_data=<landscapers_data.zip> rebuilds the folder from the original company zips (the index comes from data-tools__vault-index.js), and tools__upload-vault.js uploads the same files to Supabase Storage at each record's storage_path. Both check every file's SHA-256 against its record first, so a document can never be attached to the wrong record. Drive → Load original documents recognises each document the same way (by its SHA-256) when the app is opened by double-click.
